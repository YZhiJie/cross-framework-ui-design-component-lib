# 契约驱动双端组件库：一套 Spec 如何让 Vue 与 React 组件零漂移

> 本文基于本人维护的开源项目 XUI（@xui-design 组织，pnpm monorepo，7 个包，34 个组件，79 个测试文件）写成，全部机制均可在仓库源码中对应验证。适合正在做组件库、跨端组件抽象或前端基建的同学阅读。

## 一、问题：双端组件库为什么必然漂移

同时维护 Vue 和 React 两套组件库的团队，几乎都会遇到同一类事故：

- Vue 端 Select 多了一个 `allowCreate`，React 端没有——三个月后没人记得这是功能差异还是遗漏；
- 两端默认值不一致：Vue 端 Modal 默认宽度 520，React 端 480；
- 样式类名漂移：Vue 端叫 `xui-modal__panel`，React 端叫 `xui-modal-dialog`，共享样式包逐渐失效；
- 浮层组件在 A 端做了视口避让，B 端没做——同一个业务页面两端行为不同。

根因只有一个：**"两端应该一样"这个约束只存在于人的脑子里和 code review 的记忆里，不存在于机器可执行的检查中**。review 漏一次，漂移就永久化。

XUI 的解法是把"一样"变成一份**运行时契约（ComponentSpec）**，再用一个**契约测试脚本**在 CI 中机器化比对。下面按架构分层展开。

## 二、总体架构：七个包，依赖只允许单向向下

```text
            ┌─────────────────────────────────────┐
            │  apps/playground · apps/docs        │   演示与文档站
            └──────────────┬──────────────────────┘
                           │ 消费
      ┌────────────────────┼────────────────────┐
      ▼                    ▼                    ▼
┌───────────┐       ┌───────────┐        ┌───────────┐
│ @xui/vue  │       │ @xui/react│        │ 业务应用   │
└─────┬─────┘       └─────┬─────┘        └───────────┘
      │        ┌──────────┤
      ▼        ▼          ▼
┌─────────────────────┐  ┌──────────┐  ┌─────────┐  ┌─────────┐
│ @xui-design/core    │  │ @xui/styles│ │ @xui/icons│ │ @xui/utils│
│ 契约层（ComponentSpec）│  │ 样式单一来源│  │ 图标数据源 │  │ 工具函数 │
└─────────┬───────────┘  └──────────┘  └─────────┘  └─────────┘
          ▼
┌─────────────────────┐
│ @xui-design/shared  │   纯逻辑层：零框架依赖，双端复用
└─────────────────────┘
```

七包分工与铁律：

| 包 | 职责 | 关键约束 |
|---|---|---|
| core | 定义 ComponentSpec 契约与类型 | 不 import 任何框架；**不从 shared 导入类型**（否则 barrel 类型解析链会断） |
| shared | createXxxLogic 纯逻辑工厂 | 零框架依赖、零 DOM 依赖，类型在本地定义再由 core 对齐复用 |
| vue / react | DOM 桥接适配层 | **只做渲染，不写业务逻辑**；不得新增契约之外的 Props/事件 |
| styles | 全部组件样式的单一来源 | BEM 类名 + CSS 变量主题，双端共用同一套类名 |
| icons | SVG 数据源 | 双端共用一份图标数据，杜绝端间图标差异 |

依赖方向被 dependency-cruiser 的 12 条规则锁死（如"vue/react 只能依赖 core/shared/styles/icons/utils""shared 禁止依赖 core"），CI 中违反即红灯。**架构约束靠工具不靠自觉**，这是整套体系能长期运转的前提。

## 三、核心机制一：ComponentSpec——一份驱动两端的运行时契约

每个组件在 core 层有一份 spec，长这样（以 Button 为例）：

```ts
export const buttonSpec = {
  name: 'Button',
  props: {
    type:  { type: String },
    size:  { type: String },
    disabled: { type: Boolean },
    loading:  { type: Boolean },
    // ...
  },
  defaults: {
    type: 'default',
    size: 'md',
    disabled: false,
    loading: false,
  },
  events: {
    click: { description: '点击按钮时触发', payloadType: 'MouseEvent' },
  },
  slots: {
    default: { description: '按钮内容' },
    icon:    { description: '前置图标' },
  },
  useLogic: (props: ButtonProps) =>
    createButtonLogic({ disabled: props.disabled, loading: props.loading, onClick: props.onClick }),
} satisfies ComponentSpec<ButtonProps, ButtonEvents, ButtonSlots, ButtonLogic>;
```

四个设计点：

1. **运行时对象 + 编译期校验双保险**。`satisfies` 保证 spec 与 TypeScript 类型互相咬合——类型改了 spec 忘改，编译直接报错。
2. **默认值是契约的一部分**。`defaults` 写在 core，两端不允许各自再写默认值，从源头消灭"两端默认宽度不同"这类漂移。
3. **useLogic 指向 shared 层**。spec 直接声明该组件的状态逻辑工厂，适配层只是这个工厂的调用者。
4. **插槽显式建模**。Vue 具名插槽 ↔ React renderXxx 回调的映射关系写进契约，而不是靠文档口口相传。

## 四、核心机制二：逻辑上收 shared，适配层只剩 DOM 桥接

组件最容易产生端间差异的从来不是"长什么样"，而是"行为逻辑"。XUI 把行为逻辑全部下沉到 shared 层的纯函数工厂：

```ts
// @xui-design/shared —— create-select-logic.ts（节选）
export function createSelectLogic(options: SelectLogicOptions) {
  // 打开/关闭、键盘导航、高亮索引、选项过滤、
  // 虚拟滚动窗口计算、分组过滤、clearable 的 clear()……
  // 全部在此实现，返回状态与方法
}
```

几个代表性案例：

- **浮层视口避让**：翻转时机（首选方位空间不足且对侧更充足才翻转，防抖动）、交叉轴钳制（保底 8px 安全区）、滚动捕获 + resize 监听、rAF 合并重算、卸载自动解绑——Tooltip/Popconfirm/Select/Dropdown 共用同一实现，写一次两端生效；
- **虚拟滚动**：窗口起止计算、滚动吸附、总量估算统一在 `create-virtual-list-logic`，Select 千级选项与 Table 长列表只是把计算结果桥接到各自的 DOM 上；
- **级联关系**（Cascader/TreeSelect）：树形路径解析、父子勾选联动、禁用后代参与父级半选推导——这类最容易两端"各写一份然后微妙不同"的逻辑，全部只有一个实现。

适配层因此薄到可以审计：Vue 端一个 Select.vue 主要做 `useSelectLogic` 返回值到模板的绑定；React 端把同一份逻辑接进 JSX。**逻辑只有一个真相源，两端差异就只剩渲染语法差异**。

## 五、核心机制三：契约测试——把"两端一样"变成 CI 红灯

`scripts/contract-test.ts` 做三方比对，任何不一致直接 fail：

```text
基准：@xui-design/core 运行时 spec（name/props/defaults/events/slots）
  ├─ 对比 Vue 适配层：运行时 props 选项与 emits 选项（import 组件实例取编译产物）
  └─ 对比 React 适配层：源码静态解析（AST 提取 Props 接口与回调）

比对维度：Props 集合、事件名集合、默认值逐字段
```

它抓过的真实问题包括：Vue 端多出的契约外 prop、React 端缺失的事件、两端 `defaults` 某字段不一致。发布前这个脚本串在 `typecheck → lint → 架构检查 → 构建 → 全量测试 → 契约测试` 的门禁链里——**漂移在 CI 阶段被击毙，永远到不了用户 npm install**。

## 六、踩坑实录：契约体系逼出来的六个正确姿势

以下每一条都是真实事故的修复结晶，也是这套体系的价值证明——很多坑正是契约测试先报错，才迫使实现走向正确。

### 坑 1：`withDefaults` + 解构 = 响应式静默失效

```ts
// 错误：解构返回值会禁用 Vue 3.5 响应式解构，受控 Props 同步全部退化为一次性快照
const { value } = withDefaults(defineProps<SelectProps>(), {});

// 正确：保留 props 引用，watchEffect/模板一律 props.xxx
const props = withDefaults(defineProps<SelectProps>(), {});
watchEffect(() => syncFromProps(props.value));
```

编译器对此有警告但极易被淹没；症状是"外部改 value 组件不更新"。契约测试的受控模式用例让它在 CI 就现形。

### 坑 2：defineProps 直接引用含 onXxx 回调的完整类型

把含 `onChange` 的完整 Props 类型直接喂给 `defineProps<T>()`，SFC 编译器会把回调也编译进 props 选项——契约测试随即报"Vue 存在契约之外的 prop"。正确写法：

```ts
const props = defineProps<Omit<SelectProps, 'onChange'>>();
```

事件走 emits 声明。这条规则现在是所有含回调组件的第一反应。

### 坑 3：React useSyncExternalStore 不做快照缓存 = 无限重渲染

用 `useSyncExternalStore` 桥接 shared 逻辑层的订阅时，若 `getSnapshot` 每次返回新对象，React 判定快照变化 → 重渲染 → 再取快照 → 死循环。解法是逻辑层维护缓存的快照引用，仅在真正变更时替换。

### 坑 4：React 回调引用更新触发 useEffect 重跑

外部传入的 `onChange` 每次渲染都是新引用，挂它的 useEffect 反复执行，受控状态出现回退竞态。用 latest-ref 模式隔离：effect 依赖稳定的 ref，回调经 ref 间接调用。

### 坑 5：受控模式与 Vue 的 Boolean prop 默认转换

Vue 对缺省的 Boolean prop 会自动转 false，这会破坏"**提供了 value 就是受控、没提供就是非受控**"的约定。解法：在 `withDefaults` 第二参数中把 `value` 显式声明为 `undefined`，跳过编译器的默认转换，让 spec 层的 defaults 成为唯一默认值来源。

### 坑 6：clearable 组件的 clear() 只发 onClear 不发 onChange

清空按钮点击后 v-model 不更新的经典 bug：逻辑层 `clear()` 必须同时广播 `onChange('')`。这类"事件语义不完整"的问题同样被契约测试的受控用例覆盖。

另有工程侧两则：适配层 tsconfig 的 paths 必须指向兄弟包 **dist/types**（指向 src 触发 TS6059）；monorepo 里 turbo 的 dev 任务必须配置 dependsOn，否则多包并行启动会出现构建时序竞态。

## 七、工程闭环：让契约体系能自己活着

一个库能否长期维护，取决于改一次的成本低不低：

- **changesets 统一版本**：所有包 fixed 模式联动发版，一次变更一次 PR，CI 自动 publish；
- **bundle 预算**：check-bundle-size 脚本为每个包设 gzip 上限，新组件超线必须显式上调预算并注释原因——防止体积无声膨胀；
- **npm 发布的 access**：作用域包必须逐包声明 `publishConfig.access: 'public'`，否则发布 403；
- **文档站自动化**：从 registry 驱动生成 34 组件 × 2 语言的文档页，文档永远与代码同源；Playwright 三层 E2E（全页 smoke / 交互 / 视觉回归）守住 demo 真实行为。

最终数据：**34 个组件双端交付，双端 Props/事件/默认值零漂移由 CI 机器保证，而不是靠 review 记忆**。

## 八、这套思路的普适性

即使你不做双端组件库，"契约驱动"模式同样适用于：

- **多端小程序**（微信/支付宝/抖音）：把 spec 换成各端组件属性映射表，同样可以做三方比对；
- **设计系统落地**：Design Token 作为样式契约，两端类名与变量由 styles 单一来源约束；
- **任何"一份逻辑多端消费"** 的场景：逻辑上收纯函数层 + 消费层只做桥接 + 消费端行为机器化比对——三步凑齐，漂移无处藏身。

一句话总结：**组件库的长期主义不是写更多组件，而是让"一致"这件事从依赖人的自觉，变成依赖机器的检查。**
