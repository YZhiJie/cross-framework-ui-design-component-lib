# 01 - 跨框架组件库技术路线对比分析

## 概述

构建同时适配 Vue 和 React 的通用组件库，业界存在四种主流技术路线。本章对每种路线进行深度剖析，从架构原理、优劣势、适用场景、性能开销四个维度展开对比，并给出最终选型建议。

## 路线一：Web Components 原生方案

### 原理

使用浏览器原生 Custom Elements、Shadow DOM、HTML Templates 标准，编写标准 Web Components，在 Vue 和 React 中均可作为自定义 HTML 标签直接使用。

```
[Custom Element] ──注册──> 浏览器全局 CustomElementRegistry
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
              <my-button />            <my-button />
              Vue 模板中直接用          React JSX 中直接用
```

代表项目：**Stencil**（Ionic 团队）、**Lit**（Google）、**Fast**（Microsoft）。

### 优势

| 优势项 | 说明 |
|--------|------|
| 原生标准 | 基于 W3C 标准，不依赖任何框架运行时 |
| 真正一次编写 | 只需一套代码，所有框架零成本接入 |
| 样式隔离 | Shadow DOM 天然提供 CSS 隔离 |
| 跨框架嵌入 | Vue/React/Angular/Svelte 均可直接使用 |

### 劣势

| 劣势项 | 说明 |
|--------|------|
| 框架特性丢失 | 无法使用 Vue 的响应式系统、React 的 Hooks，开发体验退化为命令式 |
| Props 传递受限 | 属性只能传字符串或 JSON 序列化值，无法传函数/复杂对象（需通过 `el.addEventListener` 或 property 赋值绕过） |
| 事件处理繁琐 | React 对 Custom Element 事件支持差，需手写 `ref.addEventListener` 包装，React 19 才原生支持 |
| SSR 兼容差 | Shadow DOM 的 SSR 支持依赖 `declarative-shadow-dom` polyfill，Vue/React SSR 场景复杂 |
| 调试困难 | Shadow DOM 内部结构在 DevTools 中默认折叠，调试链路长 |
| 生态割裂 | 无法复用 Vue/React 的现成生态（如 v-model、Form 校验库、React Context 等） |

### 适用场景

- 面向**四框架以上**（Vue + React + Angular + Svelte）需要统一组件时
- 面向**外部开放生态**（如 Design System 给第三方使用，不限制框架）
- 组件复杂度**中低**，交互逻辑简单的展示型组件

### 性能开销

| 指标 | 数值 |
|------|------|
| 运行时依赖 | ~5KB gzip（Lit 核心）/ ~12KB gzip（Stencil runtime） |
| 首次渲染 | Custom Element `connectedCallback` 触发，有 1 帧延迟 |
| 更新性能 | 属性变化触发 `attributeChangedCallback`，批量更新需手动调度 |
| SSR 额外开销 | declarative-shadow-dom polyfill ~3KB + 服务端渲染模板注入 |

## 路线二：编译时双端转换方案

### 原理

使用单一 DSL（领域特定语言）编写组件源码，通过编译器在构建时分别转换为 Vue SFC 和 React 组件代码。

```
                    ┌── 编译器 ── Vue Plugin ──> .vue SFC 文件
.component.tsx      │
(统一 DSL 语法)  ───┤
                    └── 编译器 ── React Plugin ──> .tsx 文件
```

代表项目：**Mitosis**（Builder.io）、**Vue JSX 编译器**。

### 优势

| 优势项 | 说明 |
|--------|------|
| 开发体验好 | 单一语法，接近 JSX/模板混合体，学习成本低 |
| 输出原生代码 | 编译产物是原生 Vue/React 代码，无运行时开销 |
| 框架特性保留 | 编译后可使用 v-model、Hooks 等各自框架的原生能力 |
| Tree Shaking 友好 | 产物是标准 ES Module，Tree Shaking 效果好 |

### 劣势

| 劣势项 | 说明 |
|--------|------|
| DSL 表达力受限 | 统一语法是"两个框架的交集"，无法使用各自独有特性（如 Vue 的 `v-memo`、React 的 `useMemo` 需编译器映射） |
| 编译器复杂度 | 需要维护 AST 解析 → 转换 → 代码生成的完整编译流水线 |
| 调试映射难 | 编译后代码与源码差异大，Source Map 维护成本高 |
| 生态锁定 | 强绑定编译器工具链，IDE 插件、LSP 支持需自定义 |
| 状态管理割裂 | 编译时无法共享运行时状态实例，状态逻辑仍需在编译产物中各自实现 |

### 适用场景

- 组件数量多（>50 个）且以**展示型组件为主**
- 团队有编译器开发能力，愿意维护 DSL 工具链
- 组件交互逻辑标准化程度高，不依赖复杂框架特性

### 性能开销

| 指标 | 数值 |
|------|------|
| 运行时依赖 | 0KB（纯编译时方案，产物无额外运行时） |
| 构建耗时 | 增加编译步骤，单组件编译 ~50-100ms |
| 产物体积 | 与手写 Vue/React 组件一致，无额外开销 |
| 调试开销 | Source Map 依赖编译器质量，断点调试可能偏移 |

## 路线三：运行时适配器方案

### 原理

编写一套统一的组件描述（虚拟节点树 + 行为定义），通过运行时适配器将其渲染到 Vue 或 React 的渲染器中。

```
┌──────────────┐
│ 组件描述层    │  createElement('Button', {onClick}, [children])
│ (统一 VNode) │
└──────┬───────┘
       │
  ┌────┴────┐
  ▼         ▼
┌─────┐  ┌──────┐
│Vue  │  │React  │
│Renderer│ │Renderer│
└─────┘  └──────┘
```

代表思路：**Solid.js unify renderer**、自定义 `h()` 函数适配层。

### 优势

| 优势项 | 说明 |
|--------|------|
| 运行时共享 | 单一代码路径，逻辑真正只运行一次 |
| 灵活度高 | 可在运行时动态选择渲染器 |
| 类型统一 | 组件 API 完全一致，类型定义天然对齐 |

### 劣势

| 劣势项 | 说明 |
|--------|------|
| 渲染器开发量大 | 需要实现完整 Vue/React Renderer 接口（`createElement`/`patch`/`remove` 等） |
| 性能损耗 | 统一 VNode → 框架 VNode 的转换有额外开销，高频更新场景明显 |
| 框架生态断裂 | 无法直接使用 Vue 的 `provide/inject`、React 的 `Context`，需自建等价机制 |
| 调试黑盒 | 组件树在 DevTools 中不显示为原生 Vue/React 组件，难以定位问题 |
| 维护风险 | Vue/React 内部渲染器接口变化时，适配层需同步更新 |

### 适用场景

- 需要在**运行时动态切换框架**（如微前端场景，子应用框架不确定）
- 有自研渲染器能力的团队
- 组件以声明式渲染为主，不深度依赖框架响应式系统

### 性能开销

| 指标 | 数值 |
|------|------|
| 运行时依赖 | ~8-15KB gzip（适配器核心 + VNode 转换层） |
| 每次渲染 | VNode 树遍历 + 转换，O(n) 复杂度，n = 节点数 |
| 更新性能 | diff 算法需双层（统一层 + 框架层），约 1.5-2x 原生更新耗时 |
| 内存占用 | 统一 VNode + 框架 VNode 双份存在，内存约 1.3-1.5x |

## 路线四：共享核心逻辑 + 框架层包装（推荐方案）

### 原理

将组件逻辑拆分为三层：
1. **纯逻辑核心层**：用 TypeScript 编写框架无关的状态管理、交互逻辑、工具函数
2. **框架无关抽象层**：定义 Props/Events/Slots 的类型契约和组件接口
3. **框架适配层**：Vue 和 React 各自用原生 API（Composition API / Hooks）调用核心层，渲染模板

```
                ┌─────────────────────────┐
                │     @xui/shared (核心层)  │
                │  useCounter() / validate() │
                │  (纯 TS，零框架依赖)        │
                └───────────┬─────────────┘
                            │
                ┌───────────┴─────────────┐
                │  @xui/core (抽象层)       │
                │  ButtonProps / Events    │
                │  ComponentSpec 契约定义   │
                └───────────┬─────────────┘
                            │
              ┌─────────────┴──────────────┐
              ▼                            ▼
   ┌──────────────────┐          ┌──────────────────┐
   │  @xui/vue (适配)  │          │ @xui/react(适配) │
   │  defineComponent  │          │  forwardRef +    │
   │  + <template>     │          │  Hooks           │
   └──────────────────┘          └──────────────────┘
```

代表项目：**Headless UI**（Tailwind，Vue/React 双版本）、**Vant** 核心逻辑抽离思路。

### 优势

| 优势项 | 说明 |
|--------|------|
| 框架原生体验 | Vue 用 Composition API + SFC，React 用 Hooks + JSX，开发者体验完全原生 |
| 逻辑真正复用 | 核心层是纯 TS 逻辑，状态管理/校验/工具函数 100% 共享 |
| 类型安全 | Props/Events 类型在抽象层统一定义，双端类型自动推导 |
| 生态兼容 | 可直接使用 v-model、Form Context、React Portal 等框架原生能力 |
| 调试友好 | DevTools 中显示为原生 Vue/React 组件，调试链路完整 |
| 渐进迁移 | 可先抽核心层，再逐步补适配层，迁移风险可控 |
| Tree Shaking 最优 | 每个组件独立 ESM 导出，按需引入效果最好 |

### 劣势

| 劣势项 | 说明 |
|--------|------|
| 模板需写两份 | Vue SFC 模板和 React JSX 需各自编写（但逻辑共享，模板是声明式，差异小） |
| 接口需手动对齐 | 双端适配层需人工保证 Props/Events 行为一致，有偏差风险 |
| 响应式桥接复杂 | 核心 TS 逻辑的状态变化需通过适配层同步到 Vue ref / React state |

### 适用场景

- 面向 **Vue + React 两个框架**（不需要更多框架）
- 组件交互逻辑较复杂（表单、拖拽、虚拟滚动等），逻辑复用价值大
- 希望保持各框架原生开发体验
- 需要深度集成各框架生态（v-model、Context、Portal 等）

### 性能开销

| 指标 | 数值 |
|------|------|
| 运行时依赖 | 0-2KB gzip（核心层纯逻辑无运行时，适配层为薄包装） |
| 每次渲染 | 直接调用原生 API，无 VNode 转换开销，与手写组件一致 |
| 更新性能 | Vue ref / React state 原生更新，无额外 diff 开销 |
| 内存占用 | 与原生组件一致，核心逻辑实例共享 |

## 四方案综合对比

| 维度 | Web Components | 编译时转换 | 运行时适配器 | 核心逻辑+包装 |
|------|:-:|:-:|:-:|:-:|
| **代码复用率** | 100% | 100% | 100% | 85-95% |
| **运行时开销** | 5-12KB | 0KB | 8-15KB | 0-2KB |
| **渲染性能** | 中 | 优 | 中下 | 优 |
| **开发体验** | 差(命令式) | 中(DSL限制) | 差(黑盒) | 优(框架原生) |
| **类型安全** | 弱 | 强 | 强 | 强 |
| **框架生态兼容** | 差 | 好 | 差 | 优 |
| **调试体验** | 差 | 中 | 差 | 优 |
| **SSR 支持** | 差 | 好 | 差 | 优 |
| **实现复杂度** | 中 | 高 | 高 | 中 |
| **维护成本** | 中 | 高(编译器) | 高(渲染器) | 低-中 |
| **Tree Shaking** | 一般 | 优 | 差 | 优 |
| **适用框架数** | 任意 | 2-4 | 2-3 | 2 |

## 选型决策树

```
需要支持几个框架？
├── ≥ 3 个框架 → Web Components (路线一)
│     └── 组件交互简单？ ──是──> Stencil
│     └── 需要响应式？ ──是──> Lit + reactivity
│
└── 仅 Vue + React
      ├── 需要运行时动态切换？ ──是──> 运行时适配器 (路线三)
      │
      └── 否
          ├── 团队有编译器能力？ ──是──> 编译时转换 (路线二)
          │
          └── 否 → 共享核心逻辑+包装 (路线四) ✅ 推荐
```

## 最终选型：路线四 — 共享核心逻辑 + 框架层包装

### 选型理由

1. **目标明确**：本方案仅需支持 Vue 3 + React 17+ 两个框架，无需 Web Components 的跨框架通用性
2. **体验优先**：保持各框架原生开发体验，不引入 DSL 或编译器，降低团队学习成本
3. **性能最优**：无运行时转换开销，渲染性能与手写组件一致
4. **生态友好**：可深度集成 v-model、Form Context、React Portal 等原生能力
5. **维护可控**：无需维护编译器或渲染器，核心逻辑是纯 TS，适配层是标准框架 API
6. **渐进可行**：可以先从简单组件开始抽离核心逻辑，逐步推进，风险可控

### 与其他方案的关系

本方案在需要时也可**兼容性叠加**其他方案：
- 核心逻辑层可作为 Web Components 的逻辑来源（将核心逻辑注入 Custom Element）
- 适配层的 Props 契约可作为编译时方案的输入 schema
- 未来如果需要支持 Angular/Svelte，只需新增对应适配层
